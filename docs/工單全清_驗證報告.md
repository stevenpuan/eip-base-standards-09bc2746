## 二、這一輪修掉的東西

### 2-1 假的角色同步按鈕（org.tsx）

指派部門主管後會問「是否同時將角色設為 dept_manager？」，按「好，更新角色」**什麼都不會發生**
—— `promote()` 函式裡只有 `setPendingPromote(null); onSaved();`，完全沒有實作。

後果就是今天實查到的那件事：`department.manager_id` 是他，但推導角色仍是 member，
於是同一個人在異常缺失有主管權、在部門級報表被擋（吳巧蕙、林佩杏兩位都是這樣來的）。

已改成呼叫 `eip_set_user_roles`（與帳號管理同一條路），並保留他原有的其他角色。

### 2-2 P1#7 通用連結（NAS／http）—— 這一項我原本理解錯

規格書第五章第 8 項要的是 `entity_type / entity_id / label / url` 的**通用外部連結**，
訪談定案第 5 條「有相關檔案（NAS 或其他）可掛連結」。我先前把 `eip_link` 做成
「實體↔實體」關聯（任務連到文件／會議），那是另一件事，NAS 連結整條需求沒接到。

兩者都有用途，所以不動已上線的 `eip_link`，另建一張：

| 表 | 用途 |
|---|---|
| `eip_link` | 系統內實體關聯（任務 ↔ 文件／會議／專案／異常） |
| `eip_url_link` | **系統外的檔案與網址**（NAS UNC 或 http／file） |

- 可見性與 `eip_link` 同一把尺：**你看得到那個實體，才看得到／才能掛它的連結**
  （`eip_url_link_visible()`，刻意寫成 SECURITY INVOKER 才會沿用各表自己的 RLS）
- URL 格式在 DB 與前端都有同一條檢查：`^(https?://|file://|\\)`
- 新元件 `UrlLinks.tsx`，掛在**任務詳情**與**異常詳情**
- **UNC 路徑瀏覽器不能直接開**，所以那種一律變成「點擊複製路徑」＋提示貼到檔案總管，
  不給一個點了沒反應的連結
- 工作日誌／今日例行的「每項可掛連結」走 jsonb 既有的 `link` key，
  由同一支 `eip_set_routine_item(p_link)` 處理，不另開寫入路徑

### 2-3 P1#8 部門例行彙總補完

原本只有兩張表格。補上：

## 三、驗證過程中挖到的一個新 bug（重要）

催填功能第一次實測**回 0、什麼都沒發生**。追下去是兩層問題疊在一起：

1. `notification.entity_id` 是 **NOT NULL**，但「提醒你補填 X/X 的日誌」沒有實體可指
   （那天可能連日誌列都還不存在）→ insert 直接 23502。
   而 `eip_notification_entity_alive()` 早就寫了 `if p_entity_id is null then return true`
   ——「純訊息通知」本來就在設計裡，只是欄位的 NOT NULL 沒放開。
2. **為什麼沒被發現**：`eip_nudge_worklog` 為了「一個人失敗不要中斷整批」，
   把 emit 包在 `exception when others then raise warning`，結果硬錯誤被吞掉、函式回 0，
   從外面看就只是「按了沒反應」。

兩層都修了：

- `alter table notification alter column entity_id drop not null` ＋ 欄位註解
- `eip_nudge_worklog` 保留 per-user 隔離，但加一個出口：
  **全部都失敗就 raise**，讓系統性錯誤不能再假裝成「沒人可催」
- 前端兩個通知入口（`NotificationBell`、`notifications.tsx`）改成能吞 null：
  需要 id 的路由先確認有值，另補上 `work_log` / `handover` / `anomaly` / `leave_handover` 的導頁

這個模式值得記住：**per-item 的 try/catch 隔離，必須配一個「全部失敗就要叫出來」的出口，
否則就是把硬錯誤變成靜默失敗。**
