# 四、設計決策（避免日後反覆）

1. **個人例行範本不產生 task**，只在日誌 seed 時即時展開。
2. **子項用新表 `task_checklist`，不沿用 `parent_task_id`**（子任務當成 task 會污染看板）。
3. **子項勾選 ≠ 進度百分比**。語意是「今天有做、納入回報」，所以不動 `task.progress`。
4. **`work_log_item` 做成 JSON 的衍生投影**，不是把主資料搬過去 —— 前端不用改、可回退。
5. **例行達成率的分母**只算「當日真的有範本到期的人日」，沒建範本的人不計入（避免灌水）。
6. **所有通知一律走 `eip_emit_notification` 單一入口**，沒有任何 trigger 直接呼叫 `net.http_post`。
7. **異常缺失的開立權綁「實際部門主管」（`eip_is_dept_supervisor`）而不是 role 代碼** —— 真正管那個部門的人才能開立。
8. **`purge_guard` 機制**：永久刪除的保護寫成可註冊的檢查函式，未來要保護別的模組只要寫函式 + 更新一列設定。

# 五、施工慣例（踩過的坑）

1. **`routeTree.gen.ts` 加新路由不要跑 build** —— 會產生 790 行純排序雜訊。手工插入 7 處，diff 只 +21 行。
2. **`eslint --fix` 只跑新檔** —— `tasks.tsx` 有 323 個、`calendar.tsx` 有 87 個既有 prettier 問題，一 fix diff 會從 39 行爆成上千行。
3. **側邊欄選單是 DB 驅動**（`menus` + `role_module_permissions`），新頁面要用 migration 註冊。
4. **新 view 一律 `security_invoker = true`** —— 預設以建立者權限執行會整段繞過 RLS（0112 踩過，0113 修）。
5. **新函式一定要 `revoke execute from public`** 並用 `has_function_privilege('anon', ...)` 實測 —— 只 revoke anon/authenticated 是 no-op（0118 踩過）。
6. **守衛不要寫 `if auth.uid() is not null and <不夠格> then raise`** —— 那是 fail-open。
7. **加參數帶預設值必須 drop 舊 overload** —— Postgres 精準匹配會把舊呼叫者送去舊函式（0098、0100 各踩一次）。
8. **`ALTER TYPE ADD VALUE` 的新值不能在同交易內使用** → enum 要單獨一筆 migration。
9. **`CREATE OR REPLACE` 會重設函式 ACL** → 重寫後要再收一次權限。
10. **types.ts 沒有的新表／欄位／view** 用 `@/lib/supabase`（any 版）並於檔內宣告型別。
