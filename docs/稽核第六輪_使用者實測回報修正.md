# 稽核第六輪：使用者實測回報的修正

日期：2026-07-29
回報者：陞煇食品（一般成員身分實測，帳號 徐芷苨）
遷移：0147、0148、0149、0150、0150b、0151

## 零、這一輪的共同根因

九項回報裡有五項是同一個病：**權限判斷或結果回讀寫錯，導致只有最高權限者沒事**。

| 型態 | 具體案例 |
|---|---|
| 權限條件漏了一個角色 | `eip_can_manage_task` 只看 `owner_id`（負責人），漏了 `created_by`（建立者） |
| 結果回讀被自己的 RLS 擋住 | `eip_soft_delete` 刪完之後讀不回 `deleted_at`，把成功一律報成失敗 |
| 唯一鍵沒有排除軟刪除 | 回收區有同日日誌 → 勾選一定 23505 |
| 可見範圍當成權限用 | 請假名單靠 `qr_read` 過濾，一般成員看不到別人的假 |
| fail-silent 而非 fail-closed | 主管查管轄外個人績效回 0 列，畫面顯示成「本期沒有資料」 |

`company_admin` 在前四項都走另一條分支，所以老闆自己測完全正常。**這說明「用管理者帳號測過」不等於測過。**

## 一、BLOCKER：工作日誌無法勾選（23505 duplicate key）

**現象**：一般成員勾選工作項目，右上角跳
`duplicate key value violates unique constraint "work_log_tenant_id_user_id_log_date_key"`。

**根因**：`work_log` 的唯一鍵是 `UNIQUE (tenant_id, user_id, log_date)`，**沒有排除軟刪除**。
`eip_set_routine_item` 找當日日誌時帶了 `deleted_at is null`：

```sql
select * into v_log from public.work_log
 where user_id = v_me and log_date = p_date and deleted_at is null;   -- 找不到
if v_log.id is null then insert into public.work_log ...               -- 撞唯一鍵
```

只要使用者曾經把當天的日誌丟進回收區，之後任何勾選都必爆。
實查當天有 **3 個人**踩到（徐芷苨、吳巧蕙、林子語），全部是 `deleted_at` 有值的當日日誌。

**修法（0147）**：
- 唯一約束改成 partial unique index：`... where deleted_at is null`。
  一人一天只能有一份「未刪除」的日誌，回收區的舊日誌不再擋住新建。
- `eip_set_routine_item` 的 insert 補上 `unique_violation` 的收斂 —— 雙擊或兩個分頁同時勾時，
  抓現成的那筆繼續，不要把競態變成錯誤訊息。
- 確認過全庫沒有任何函式對 `work_log` 用 `on conflict`，改索引不會打到別人。

**實測**：以徐芷苨身分呼叫 `eip_my_routine_today` 拿到她畫面上那三項（EIP測試／官網訂單／QP肉鬆），
勾第一項回 `{"ok": true, "routine_done": 1, "routine_total": 3}`。原本必爆的路徑通了。

## 二、BLOCKER：任務協作者加不進去（42501）

**現象**：建立任務後跳「任務已建立，但協作者未加入，請手動補上」。

**根因**：`task_collaborator` 的寫入政策是 `eip_can_manage_task(task_id)`，而那支函式只認：

```
company_admin  or  t.owner_id = auth.uid()  or  dept_manager 且管轄該部門
```

**漏了 `created_by`**。所以「我建立、指派給別人」的任務，建立者自己不能加協作者。
`task` 表本身的 UPDATE 政策有含 `created_by`，所以改標題正常、只有子表炸 —— 這也是為什麼看起來很隨機。

**修法（0147）**：`eip_can_manage_task` 補 `or t.created_by = auth.uid()`。
全庫只有 `task_collaborator` 一條政策用這支函式，一處修完全部收斂。

**實測**（徐芷苨身分）：
- 自己當負責人 → 加協作者 OK（原本就 OK）
- **指派給別人 → 加協作者：修前 42501，修後 OK**
- 移除協作者 OK

**「協作者不能選我自己」**：這是另一件事。選單排除的是**負責人**（預設就是自己），語意上正確，
但沒有告訴使用者為什麼。前端在建立與編輯對話框都補了一行說明：
`負責人（某某）不需要重複加為協作者`。

## 三、BLOCKER：`eip_soft_delete` 把成功的刪除一律報成失敗

這一項使用者沒有單獨列出來，是我在跑權限實測時撞到的，**影響所有角色、所有納管模組**。

**根因**：這支是 `SECURITY INVOKER`（刻意的，要讓 RLS 決定能不能刪）。
但它刪完之後用**同一個身分**再讀回 `deleted_at` 來判斷結果：

```sql
delete from task where id = $1;             -- guard 改成軟刪除，RETURN NULL
select deleted_at from task where id = $1;  -- ← 一定讀不到
```

因為 `task_read` 政策結尾是 `and deleted_at is null`（0095／0111 加的，**連 company_admin 也套用**），
列一旦被軟刪除就對所有人隱形 → `v_after` 永遠 null → 回 `{ok:false, reason:'無刪除權限'}`。

使用者按刪除 → 資料其實已經進回收區，畫面卻說「刪除失敗：僅本人／本部門主管／管理者可刪除」。

**為什麼前幾輪沒抓到**：我用 `postgres` 身分測（RLS 直接繞過），read-back 讀得到。
**這是我這次學到的第三類檢查盲點**：SECURITY INVOKER 函式一定要用真實角色測，不能用 postgres。

**修法（0150 → 0150b）**：
第一版加了一支 DEFINER 小函式回讀，結果 `authenticated` 反而被 42501 擋在那支 helper 前面，
要修就得把 helper 開給前端 —— 等於多開一個可以探測任意 id 是否存在的介面，不划算。
第二版改成**不需要繞過 RLS 的判斷**：

| 刪除後的狀態 | 結論 |
|---|---|
| 列已看不見 | 成功（軟刪除生效，或這張表是硬刪除） |
| 列還看得見且 `deleted_at` 仍為 null | DELETE 被 RLS 擋掉 |
| 列還看得見且 `deleted_at` 有值 | 該模組沒隱藏軟刪除，也算成功 |

三種情況都不必 definer，也不會多洩漏任何資料。

**實測**（徐芷苨身分）：刪自己的任務 → `ok:true`；刪別人的 company 可見任務 → `ok:false 無刪除權限`；
刪自己的個人行程 → `ok:true`。九個納管模組的 `module_key`／`table_name` 也一併核對過。

## 四、行事曆看不到請假名單

**根因**：請假走 view `eip_calendar_events`（`security_invoker = true`），
所以受 `eip_quick_report` 的 `qr_read` 限制 —— 只看得到自己的、自己代理的、自己被指派代辦的。
實測一般成員直接讀 `eip_quick_report` 是 **0 筆**。

**定案**：「誰在哪一天請假」是全公司都該知道的事，**但「事由」不是**。
所以不放寬 `qr_read`，另開一支 `SECURITY DEFINER` 的 `eip_leave_roster(p_from, p_to)`（0148），
只回姓名／部門／區間／是否全天／代辦是否完成，**不回 `detail`、不回 `leave_type`**。

**實測**：同一個一般成員身分，`eip_leave_roster` 回 **12 筆**，直接讀 `eip_quick_report` 仍是 **0 筆**。
名單看得到、事由沒外洩。

前端（`calendar.tsx`）：
- 請假改讀這支 RPC，`queryKey` 帶上月份範圍（原本 `["cal","leave"]` 沒帶範圍，切月不重抓）
- 篩選列下方新增「今日請假」區塊，全員可見；沒人請假顯示「今天沒有人請假」；RPC 失敗顯示錯誤＋重試
- 請假事件不再做成可點連結（一般成員沒有權限看詳情，點了會空白），改成 tooltip
- `handover_done = false` 時標記「代辦未完成」

## 五、行事曆每天的事項無法展開／收合

**根因**：`evs.slice(0, 4)` 加一行純文字 `+N`，點不動，第 5 筆之後永遠看不到。

**修法**：`+N` 改成按鈕，逐格展開／收合（`expandedDays: Set<ymd>`），
日格改 `h-auto` 讓展開時能長高；篩選列加「全部展開／全部收合」（本月沒有任何格子超過 4 筆時不顯示，
避免一顆按不出效果的死按鈕）。

## 六、任務建立畫面缺欄位、編輯畫面缺協作者

**建立對話框**新增：
- **子項清單**：可增刪的標題列，建立後寫入 `task_checklist`（`sort_order` 明確給值，
  批次 insert 靠 trigger 補不保證畫面順序）
- **相關連結**：標籤＋網址，寫入 `eip_url_link`（`entity_type='task'`），
  送出前就用 `validateExternalUrl()` 驗格式，不要等 DB 回 23514
- 「檔案」用 NAS 路徑連結涵蓋；建立對話框刻意**不做真正的檔案上傳**（那是文件中心的範圍）

**編輯對話框**新增協作者區塊：
- 儲存時做**差集**（新增 insert、移除 delete），**不是全刪全插** ——
  `trg_task_collab_change` 會寫變更紀錄，全刪全插會在「執行歷程」時間軸製造一堆假事件
- 載入失敗時跳過同步而不是拿空集合去比（否則一次網路錯誤會把所有協作者刪掉），
  並顯示「協作者載入失敗＋重試」
- `task_collaborator` 沒有 `id` 欄位（PK 是 `task_id + user_id`），列數檢查要用 `.select("user_id")`

## 七、請假代辦改回「可事後補登」

**使用者原話**：「應改為當初的設定，因為有時候臨時請假不一定馬上可以把交接登打仔細。
關於交接代辦事項及代理人相關資訊，應該讓員工於『交接代辦』區塊操作。」

上一輪把「區間＋代理人（必填）＋逐項代辦」綁成一張表單一次填完，**方向錯了** ——
臨時請假的人填不完，結果假送不出去。

**前端**：
- `LeaveRequestDialog`：代理人改**選填**；代辦清單改**預設收起**（點「順便填代辦事項」才展開）；
  `items` 初始值改成空陣列；收起狀態一律不送代辦。只填區間就能送出。
- `handover.tsx` 新增「我的請假交接」區塊（放在頁面最上方，不是第四個分頁 ——
  現有 Tabs 的 value 直接當 `eip_handover_item.status` 查詢條件，塞一個非狀態的分頁會讓那支
  query 與表格欄位語意破掉；而且臨時請假回來的人需要一進頁面就看到要補登）。
  可就地指定／更改代理人、新增／編輯／刪除代辦、看完成度。
  **已完成的項目不可刪也不可改標題**（避免把別人做完的紀錄改掉）。
- `quick-reports.tsx` 拿掉「未指定代理人就不准新增代辦」的擋阻，兩頁行為一致。

**後端（0149）** —— 這個流程改變帶出兩個缺口：

| 缺口 | 修法 |
|---|---|
| 事後才指定代理人時，既有「未指派」的代辦不會自動掛給他（`eip_fill_lhi_defaults` 掛在項目表，改請假單不會觸發） | 新增 `trg_lhi_backfill_on_deputy_set`：`deputy_id` 變更時回填 `assignee_id is null and done_at is null` 的項目。已完成的不動，完成者要留著 |
| `lhi_update` 的 USING／WITH CHECK 都是 `eip_can_see_leave()`，代理人可以改掉請假本人寫的事項標題與指派對象。事後補登的流程下更容易發生（同一份清單多人同時碰） | 新增 `trg_lhi_edit_guard`：非本人／非管理者只能改 `done_at`／`done_by`，改內容一律 42501。用 trigger 而不是 RLS，因為 RLS 沒有欄位粒度 |

**實測**：未指派代辦 → 事後指定代理人 → 自動回填 OK；代理人勾完成 OK；
代理人改標題 → 被擋 42501 OK；本人改標題 OK；全部完成後單據自動 `done` OK。

## 八、部門例行彙總的數字

**使用者原話**：「應做的數量不對，我只有新增 2 個，但是跑出 30 個？」「達成率計算方式好像需要修改？已做/應做=達成率」

**查證結果：計算是對的，問題全在標示。**
- RPC 回「一人一天一列」，KPI 磚把整個期間的 `expected` 加總。預設 14 天 → 2 個每日範本 × 15 天 = 30。
- 達成率**本來就是** `done 合計 ÷ expected 合計`，跟使用者要的一致。
  是分母 30 看起來莫名其妙，連帶讓人懷疑算法。

所以這一輪做的是**讓數字自己解釋清楚**：

| 改動 | 內容 |
|---|---|
| 磚標籤 | `應做項數` → **`應做項次`**（同 `已做項次`） |
| 磚副標 | `期間 14 天，其中 10 天有例行；平均每天 3.0 項`。**刻意不寫「14 天 × 平均 2.1 項/天」** —— 有空白天數時乘不回去，讀者拿計算機一驗又會認為系統算錯，那正是這次客訴的成因 |
| 達成率副標 | 寫出實際代入的數字 `已做 18 ÷ 應做 30` |
| 未提交人日副標 | 說明「人日」是一人一天算一列 |
| 「依人」表格 | 新增 **`天數`** 欄，插在應做前面 —— `2 個範本 × 15 天 = 30` 在表格上自己看得出來 |
| 預設範圍 | `14 天` → **`今天`**。主管打開這頁最常問的是「今天大家做了沒」，預設 14 天累計是誤解主因 |
| Excel 匯出 | 一併加天數欄，標題改「應做項次／已做項次」 |
| 頁面說明 | 重寫：一人一天一列的累計 → 磚上是項次不是範本數 → 應做／已做定義 → 達成率是整體加總相除、非各列比率平均 |

順手修掉 `listQ` 的 `queryKey` 只帶 `days` 但 `queryFn` 讀 `from`/`to` 的問題（跨午夜會回昨天的區間）。

## 九、順手修掉的「靜默失敗」（同一類病）

這幾處都是**被 RLS 擋掉時看起來成功**，正是使用者說「不同權限的人會報錯」的另一半 ——
有些甚至連錯都不報。

| 位置 | 原本 | 修法 |
|---|---|---|
| `tasks.tsx` 看板拖拉換狀態 | `.update()` 無列數檢查，沒權限時卡片默默彈回、無訊息 | 補 `.select("id")`，0 列從 `mutationFn` throw 讓 React Query 正常回滾，`onError` 一律 invalidate 後再 toast |
| `tasks.tsx` 單筆刪除 | `.delete()` + 只看 error → 一律跳「任務已刪除」 | 改走 `eip_soft_delete` RPC。**列數檢查在 `task` 上不能用**：軟刪除 guard 是 `BEFORE DELETE ... RETURN NULL`，ROW_COUNT 一律 0，會把成功報成失敗 |
| `my-tasks.tsx` 刪除 | 同上（最後一處） | 同上。順手改掉錯誤文案：這不是永久刪除，會進回收區 |
| `tasks.tsx` 補充說明 編輯／刪除 | 無列數檢查，RLS 擋掉後那則說明重新載入又出現 | 補列數檢查。這張表是硬刪除，列數可信 |
| `tasks.tsx` 任務本體儲存 | 無列數檢查 | 補。訊息刻意保留餘地 —— `RETURNING` 也受 SELECT 政策約束，主管把任務移到別的部門可能 0 列但其實成功 |
| `eip_performance_summary` | 主管查管轄外個人 → 回 0 列，畫面顯示「本期沒有資料」 | **0151** 改 fail-closed：`權限不足：這位同仁不在你的管轄範圍內`；部門參數同樣處理 |

## 十一、兩個你指定必查的類別

### ① 表上的 trigger
- 公開 schema 非內部 trigger **72 個，停用 0 個**
- 本輪新增的兩個都在：`trg_lhi_backfill_on_deputy_set`、`trg_lhi_edit_guard`

### ② 外部服務的真實回應
`net._http_response` 近 24 小時 5 次呼叫，**HTTP status code 全部 200**。
但逐筆讀 body：

```json
{"line_status":429,"line_body":"{\"message\":\"You have reached your monthly limit.\"}"}
```

**LINE 月額度仍然用盡，還沒恢復。** 只看 status code 會誤判成已恢復 ——

## 十四、我這次學到的檢查盲點（加入常設檢查範圍）

前幾輪已經記過兩類（**表上的 trigger**、**外部服務的真實回應**）。這一輪要加第三類：

> **SECURITY INVOKER 的函式，一定要用真實角色的 JWT 測，不能用 `postgres`。**

`eip_soft_delete` 的 bug 完全是這個原因躲掉的：用 postgres 測時 RLS 被繞過，
刪完讀得回 `deleted_at`，一切正常；換成 authenticated 就 100% 失敗。

同理，**「用管理者帳號測過」不等於測過** —— 這一輪五個問題裡有四個，
`company_admin` 都走另一條分支。
