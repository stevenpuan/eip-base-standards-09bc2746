## 七、下次接手一定要先知道的（踩過的坑）

### 資料庫
1. **RLS 的 PERMISSIVE 政策是 OR** —— 加政策只會放寬，不會收緊
2. **`deleted_at is null` 只能加在 USING，不能加在 WITH CHECK** —— 否則軟刪除自己那筆 UPDATE 會被擋
3. **軟刪除 guard 是 `BEFORE DELETE ... RETURN NULL`** —— `task` 的 DELETE 一律回 0 列，列數檢查在這張表上會把成功報成失敗，必須走 `eip_soft_delete` RPC
4. **`CREATE`（非 `OR REPLACE`）會套用 schema 預設權限，包含 `anon` EXECUTE** —— DROP+CREATE 之後要重新 revoke
5. **`CREATE OR REPLACE` 會重設函式 ACL** —— 改完要再收一次權限
6. **RETURNS TABLE 的 OUT 欄位是 plpgsql 變數，會與表欄位撞名（42702）** —— 查詢要加表別名
7. **改 OUT 參數名要先 `DROP FUNCTION`**（42P13）；**加帶預設值的參數會產生 overload 歧義** —— 要 drop 舊簽章
8. **`ALTER TYPE ADD VALUE` 的新值不能在同交易內使用** —— enum 要獨立一筆 migration
9. **新 view 一律 `security_invoker = true`** —— 預設會以建立者權限執行，整段繞過 RLS
10. **政策運算式以查詢者身分執行** —— 政策裡呼叫的函式，該角色必須有 EXECUTE，否則連判斷都做不到就 42501
11. **`SECURITY INVOKER` 的函式一定要用真實角色的 JWT 測，不能用 `postgres`** —— 第 3 件 BLOCKER 就是這樣躲掉的

### 前端
1. **PostgREST 的 UPDATE／DELETE 被 RLS 擋住時回 0 列且 `error === null`** —— 每個寫入都要 `.select(...)` 檢查列數
2. **`task_collaborator` 沒有 `id` 欄位**（PK 是 `task_id + user_id`）—— `.select("id")` 會直接報錯
3. **`toISOString()` 在 UTC+8 會退回前一天** —— 取本地日期一律 `toLocaleDateString("sv-SE")`
4. **`npm run build` 會重寫 `src/routeTree.gen.ts`** 成跟 Lovable 不一致的形狀（所有 `<Link>` 都要求 `search`）—— 一律還原成 main 的版本，不進 commit
5. **不要跑 prettier／eslint --fix** —— 多數檔案有數百個既有 prettier 問題，一 fix diff 會從幾十行爆成上千行
6. **字級用 `text-[11.5px]` / `text-[12.5px]`** —— Lovable 做過全站調整，全 repo 已無 `10px`／`11px`
7. **`queryKey` 要帶齊 `queryFn` 實際讀到的變數**（尤其日期）—— 跨午夜會回到昨天的資料
8. **寫入後一定要 `invalidateQueries`** —— `refetchOnWindowFocus` 預設 true，舊快照會蓋回樂觀狀態

### 流程
1. **git patch 一次只放一個 commit**，給指令前先 `git ls-remote` 確認 `main` 的實際位置 —— 這兩天的混亂都是「假設了前置狀態卻沒驗證」
2. **`git push origin --delete` 一次刪多個分支時，前面的已經生效**，錯誤訊息只反映最後失敗的那一個
3. **merge 完再刪分支**，不要把開 PR 與刪分支寫在同一段指令裡
4. **Lovable 會直接推 main**（今天推了字型／版面／權限修正多筆）—— 每次要先 `git fetch` 再決定基底，必要時 rebase

## 八、常設檢查範圍（累積六類）

1. **表上的 trigger**（Steven 指定）
2. **外部服務的真實回應 —— 要讀 body，不能只看 status code**（Steven 指定；`line-push` 一律回 HTTP 200，真正狀態在 body 的 `line_status`）
3. **`SECURITY INVOKER` 的函式一定要用真實角色的 JWT 測，不能用 `postgres`**
4. **有資料之後要回頭對帳，不能只驗「程式看起來對」**
5. **判斷寫入結果只能看實際落地的值** —— `found`、「沒報錯」、回傳列數都可能騙人（軟刪除 guard 讓成功回 0 列；守衛 trigger 讓失敗回 1 列）
6. **權限一律綁事實，不綁角色代碼或所屬位置** —— 角色代碼會被誤設、所屬部門會被調動，兩者都不代表職責
