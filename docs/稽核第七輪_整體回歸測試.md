## 一、BLOCKER：日誌建立之後才新增的例行範本，當天永遠不會出現

### 怎麼抓到的
拿 `eip_dept_routine_summary` 的輸出跟我自己從原始資料手算的結果對帳，合計一致（137／5），
但逐人比對「今日到期範本數」與「`eip_my_routine_today` 回傳項數」時，**王柔蓁 5 筆範本只出現 3 項**。

### 根因（時間戳精確對得上）

| 時間（UTC） | 事件 |
|---|---|
| 04:57:43 | 建範本「文件歸檔」 |
| 04:58:23 | 建範本「覆核訂單」 |
| 04:58:43 | 建範本「製作/核對晚班總表」 |
| **04:59:19** | **當天的 `work_log` 被建立 → jsonb 快照了那 3 項** |
| 05:00:01 | 建範本「製作/核對明早總表」 ← 今天不會出現 |
| 05:01:06 | 建範本「製作/核對應附袋」 ← 今天不會出現 |

日誌的 jsonb 是**建立當下的快照**，`eip_my_routine_today` 有日誌就直接讀 jsonb，
沒有任何機制把後來新增的到期範本補進去。

**後果不只是「少看到兩項」**：`eip_dept_routine_summary` 的 `expected` 是即時從範本算的（5），
`done` 只能從日誌來（最多 3）→ 她的例行達成率**永遠卡在 60%**，
而且她一定會回報「我新增的例行沒出現」。

**上線前這會大量發生**：所有人都在今天建範本，多數人的日誌已經先存在了。

### 為什麼不能單純「補齊缺的項目」
`eip_remove_routine_item`（第四輪為了「例行工作沒加刪除的功能」加的）是把元素**從 jsonb 真的刪掉**。
單純補齊會把使用者刻意移除的「今天不做這項」全部救回來，等於把上一輪的功能廢掉。

### 修法（0153）——三件一起改
1. **移除改成墓碑**：有 `source` + `ref_id` 的項目（範本／常態工作衍生的）不再刪除元素，
   改標記 `{"removed": true, "done": false}`。使用者自己打的一次性項目沒有來源，照舊直接刪。
2. **新增 `eip_topup_routine_log(user, date)`**：重新算一次 seed，把「seed 有、日誌裡（**含墓碑**）
   找不到同一個 `source+ref_id`」的項目補進對應時段。
   **只補 `status = 'draft'` 的日誌** —— 已送出的不動，那會改寫歷史。
3. **`eip_my_routine_today` 先補齊再回傳**，並濾掉墓碑。它原本是 `STABLE`，補齊要寫入，
   所以改成 `VOLATILE`（要先 `DROP` 才能改）。
4. `eip_dept_routine_summary` 的 `done` 也排除墓碑，否則「勾過又移除」會被算成已做。

### 實測（王柔蓁本人身分）

| 檢查 | 結果 |
|---|---|
| 今日清單項數 | **3 → 5**（等於範本數） |
| 勾剛補進來的「應附袋」 | OK，`routine_total` 回 5 |
| 移除該項後再讀 | 4 項，**補齊沒有把它救回來** |
| 部門彙總的已做合計 | 5（墓碑那項雖然勾過，正確地不計入） |

## 二、BLOCKER：`acknowledged` 讓現有 11／13 張請假單整塊鎖死

### 現象
新的「我的請假交接」把 `acknowledged` 當已結案（`LEAVE_CLOSED = {done, acknowledged, closed}`），
但 `quick-reports.tsx` 的 `DONE_STATUSES` 是 `{done, closed}` —— 同一份資料兩頁講不同的話。

實查正式庫：13 張未刪除的請假單裡 **11 張是 `acknowledged`**。那 11 張在新區塊全部顯示綠色
「已結案」、預設被濾掉看不到、代理人不能改、代辦不能增刪改。**功能對現有資料幾乎全滅。**

### 審查者給的失敗情境是錯的，但 bug 是真的
審查 agent 說「代辦被取消完成 → trigger 退回 `acknowledged`」。我查了 `eip_lhi_rollup`，
它退回的是 **`open`**，而且原始碼註解就寫著「不要用 `acknowledged`：那是舊制留下的值，
前端把它當已完成顯示，退回到那裡會讓畫面說謊」—— 那正是第五輪（0145）刻意改掉的。

真正的來源是**舊資料**：舊制請假要主管核准，`acknowledged` = 主管已確認。
新制（定案第 14 條）主管不核准，這個值已經沒有意義，但歷史資料還帶著它。

### 修法（0152）—— 從資料層拿掉歧義，不要每個前端各自特判
實查這 13 張的共同特徵：**全部單日假、0 筆代辦、沒有代理人、假期都已結束**，
也就是沒有任何未完成的交接。

1. 已結束且沒有代辦的 → `closed`（用 `closed` 而非 `done`，讓「沒有代辦直接結案」
   跟「代辦全部完成」在資料上分得出來）
2. 還沒結束或有代辦的舊 `acknowledged` → `open`（交回新制的完成度推導）
3. **加 CHECK 約束** `not (type='leave' and status='acknowledged')` —— 讓這個值不會再回到請假身上。
   `late`／`other` 保留這個值，那邊「主管已確認」是有意義的。

先確認過全庫只有 `eip_lhi_rollup` 提到 `acknowledged`，而且是在註解裡說「不要用它」，
沒有任何函式會寫入，所以加約束不會打到現有流程。

結果：`leave` 的狀態分佈現在是 `{closed: 13}`，`acknowledged` 為 **0**。

前端同步修正：常數移到 `src/lib/eip-constants.ts` 的 `LEAVE_DONE_STATUSES`，兩頁共用同一份 ——
它們會漂移就是因為各寫一份。

  三種情況都不會反向刪資料。

## 四、掛帳兩輪的兩項，這輪驗掉了

### ① 交接佇列的協作者項目，換人後會不會自動結案 → **會**
`eip_sweep_handover` 對 `task_collaborator` 的結案條件是「該任務上已經沒有離職者的協作紀錄」。

| 步驟 | 結果 |

| 協作紀錄還在 → 跑 sweep | `status = pending`（正確地不結案） |
| 移除離職者、加入接手的人 → 跑 sweep | **`status = resolved`，自動結案** |

第六輪之前那顆「前往處理」是死路（編輯對話框沒有協作者欄位），現在整條路通了。

`trg_lhi_edit_guard`：代理人可以勾完成，改標題被 42501 擋，請假本人可以改。
用真實 JWT 冒充身分測過，走的是同一條 RLS ＋ trigger 路徑。
