## 一、CRITICAL：管轄範圍可以從「坐在哪個部門」推出來

### 事實

正式庫帳號 **曾義仁**：

| 項目 | 狀態 |
|---|---|
| `dept_manager` 角色代碼 | 有 |
| `department.manager_id` 指向他的部門 | **一個都沒有** |
| 所屬部門 | 總經理室 |
| 總經理室子樹底下有幾個部門 | **17 個（等於全公司）** |

實測他當時可以：讀部門例行彙總、讀依部門績效、用催填、**修改與刪除全公司 17 個部門的
`task` / `meeting` / `project` / `eip_document` / `recurring_rule` / `eip_quick_report`**。

### 根因：兩支函式各出一半的力

```sql
-- 1) 報表閘門：只看角色代碼
eip_is_any_dept_supervisor()
  current_role_name() in ('company_admin','dept_manager')   -- ← 有角色就過

-- 2) 管轄範圍：把「所屬部門」也算成管轄
eip_user_can_scope_dept(p_dept)
  with roots as (select current_department_id() ...          -- ← 坐在那裡就算管那裡
                 union select 他管的部門)
```

配合 11 條政策裡的 `dept_manager AND eip_user_can_scope_dept(dept)`，兩者相乘就把他
變成事實上的全公司管理者。

**這跟第四輪就定下的原則直接矛盾**：「異常缺失的開立權綁『實際部門主管』
（`eip_is_dept_supervisor`）而不是 role 代碼」。當時我只把 `eip_is_dept_supervisor` 改對，
這兩支漏掉，而它們才是報表與寫入權限的實際守門人。

### 修法（0157）與定案調整（0158）

**0157**：兩支都改成只認事實 —— `department.manager_id`。

動手前逐人做集合差，確認影響範圍：

| 對象 | 影響 |
|---|---|
| 曾義仁 | 失去 17 個部門 |
| 其餘 8 位 `dept_manager`、4 位 `company_admin` | **0 變動**（每位的實際管轄都 ⊇ 所屬部門） |
| 12 位 `member` | 帳面上失去自己的部門，但 11 條政策全部有 `dept_manager` 角色守門，**實際 0 變動** |
| 成員看部門範圍資料 | 走的是 `eip_can_view_dept_record` 的第二條分支 `eip_dept_in_subtree(自己的部門, 目標部門)`，**不受影響** |

**0158**：老闆定案「曾義仁為總經理室，權限保留」。

不退回 0157 —— 退回等於下一個被放進總經理室又拿到角色代碼的人會再次無聲取得同樣權限。
改成**明確登記**：新增 `eip_dept_supervisor(department_id, user_id)` 對應表
（`department.manager_id` 只能有一個，實務上總經理室需要兩位督導），
管轄 = `manager_id` ∪ 明確登記，各自往子樹展開。

登記一筆：曾義仁 → 總經理室，`note` 寫明「定案保留原有權限，原本靠所屬部門＋角色代碼取得」。

### 驗證（兩個方向都測）

|---|---|
| 曾義仁（已登記） | 可管部門數 **17**、部門例行彙總 31 列、依部門績效 14 列、催填 OK、異常週KPI 2 列、改別部門任務 OK → **權限完全保留** |

## 二、未登入請求會噴看不懂的錯（正在發生）

### 事實
正式庫日誌，台北 20:14–21:02 共 **25 次**：

```
ERROR: permission denied for function current_tenant_id
```

重現後發現**不同表三種行為**：

| 未登入讀取 | 修前 |
|---|---|
| `task` | 42501 permission denied for **function** `current_tenant_id` |
| `work_log` | 0 列（乾淨） |
| `notification` | 42501 permission denied for **table** |

### 根因
85 條 RLS 政策是 `TO public`（含 `anon`），政策內部呼叫 `current_tenant_id()` 等判定函式。
但前幾輪為了追求「anon 可呼叫函式 = 0」把它們從 `anon` 收回了 ——
**政策運算式是以查詢者身分執行的**，所以未登入連「判斷有沒有權限」都做不到就先炸。

分頁開一整天、token 過期之後正好會踩到：使用者看到紅色錯誤，而不是「請重新登入」。

### 修法（0154、0155）
把 **11 支政策判定器／身分讀取器**開回給 `anon`。動手前逐支實測 `auth.uid()` 為 null 時
**全部回 `false`**，所以開放之後每條政策都成立不了 → 一律 0 列、寫入一律被拒，
實際可及範圍沒有增加、資訊洩漏為零。

掃全部 73 張 RLS 表：**乾淨 73、函式權限錯誤 0、未登入看得到資料 0**。

順手（0156）：`eip_deletion_policy` 的讀取政策是 `using (true)` 且 `TO public`，
未登入就看得到 9 列納管設定。改成需登入。

### 一個我要更正的指標
我報了六輪的「anon 可呼叫函式 = 0」**是錯的目標**，追求它反而製造了這個 bug。
新口徑：

> anon 可呼叫函式 = **11**，且全部是政策判定器／身分讀取器，未登入一律回 false／NULL。
> **業務 RPC 仍必須是 0。**

理由寫進 migration 註解，免得下一輪有人看到 11 當成漏洞收回去，把 bug 帶回來。

## 四、錯誤訊息統一

老闆看到的畫面是這個：

> duplicate key value violates unique constraint "work_log_tenant_id_user_id_log_date_key"

根因不是資料庫，是**前端把 `error.message` 原封不動丟進 toast**。
一般同仁看到這種字串只會覺得系統壞了，不知道自己做錯什麼、也不知道下一步該做什麼。

### 做法：一個集中的轉譯層，不是每頁各寫 if-else
新增 `src/lib/eip-error.ts` 的 `humanizeError(err, ctx?)`，判斷順序由可靠到不可靠：

1. **`P0001` → 原樣透出**（這是後端 `raise exception` 的自訂中文，本來就是寫給使用者看的，
   例如「有協同者、變更紀錄或進度回報的任務不可永久刪除」、「今天的日誌還沒到期，不能催填」、
   「只有請假本人可以修改代辦事項的內容」）。**連 ctx 前綴都不加**，否則會話中有話。
2. 前端自己 `throw new Error("中文…")` 的訊息 → 原樣透出（同性質）
3. `23505`／`23514` → 先查 constraint 名稱表給具體訊息
4. 其餘 SQLSTATE 查表（42501／23503／23502／22P02／PGRST116／40001／57014…）
5. 網路類 → 「連線中斷，請確認網路後重試」
6. 其他 → 「操作失敗（代碼 X）。若持續發生請把這個代碼提供給系統維護者」
   —— **保留代碼**，不要藏掉，否則以後查不到問題

截圖那條現在是：

> 儲存日誌失敗：今天的工作日誌已經存在了，請重新整理頁面再操作

### 範圍
**161 處、44 個檔案**。除了 toast，也接了會顯示在畫面上的 state
（`setErr` / `setOpErr` / `setLoadErr` / `setCollabErr` / `setTimelineErr` / `setNotesErr`…）。
`console.error` 一律沒動 —— 那是給開發看的，原始訊息很重要。

constraint 名稱已對正式庫的 `pg_constraint` 逐一核對，**全部對得上**
（`work_log_live_tenant_user_date_uniq` 是 partial unique index 不在 `pg_constraint`，
但錯誤訊息會帶索引名，前綴比對成立）。

### 順手修的三個既有缺陷
| 位置 | 問題 |
|---|---|
| `src/lib/eip-user.tsx` | `e instanceof Error ? e.message : String(e)` —— PostgrestError 是純物件不是 Error，所以「取得 EIP 身分」失敗時畫面上顯示的字面是 **`[object Object]`** |
| `eip/assistant.tsx` | `throw new Error(error.message)` 把 `code`／`status` 丟掉，轉譯層拿不到訊號 |
| `eip/documents.tsx:904` | 巢狀的原始訊息會整串溜過轉譯層 |

## 十、常設檢查範圍（累積四類）

1. **表上的 trigger**（你指定）
2. **外部服務的真實回應 —— 要讀 body，不能只看 status code**（你指定）
3. **SECURITY INVOKER 的函式一定要用真實角色的 JWT 測，不能用 `postgres`**（第六輪 `eip_soft_delete`）
4. **有資料之後要回頭對帳，不能只驗「程式看起來對」**（第七輪 例行補齊）

這一輪再加第五、第六類：

5. **判斷寫入結果只能看實際落地的值。** `found`、「沒報錯」、回傳列數都可能騙人 ——
   軟刪除 guard 讓成功回 0 列，守衛 trigger 讓失敗回 1 列。

   兩者都不代表職責。這一輪最嚴重的漏洞就是這兩者相乘的結果。

## 十一、追加（0159）：沒有主管就往上一階一階找

定案：「沒有主管，就往上上階的主管跑」。

### 現況：6 個部門找不到直屬在職主管

| 部門 | 問題 | 實際負責人 | 跳幾階 |
|---|---|---|---|
| 業務部 | 未指派 | 總經理室／曾俊凱 | 1 |
| 學校課 | 未指派 | 總經理室／曾俊凱 | **2**（業務部也沒有） |
| 財務部 | 未指派 | 總經理室／曾俊凱 | 1 |
| 電宰會計課 | **主管孫倩筠已停用** | 總經理室／曾俊凱 | **2**（財務部也沒有） |
| 分切課 | 未指派 | 生產部／曾于庭 | 1 |
| 衛管課 | 未指派 | 行政部／王儷瑾 | 1 |

### 三個地方原本只往上一階就放棄

| 位置 | 原本 | 後果 |
|---|---|---|
| `eip_notification_recipients` 安全網① | 只查 `parent_id` | 學校課、電宰會計課的部門通知直接落到管理者，不是曾俊凱 |
| `eip_handover_assignee` 步驟 3 | 只查 `parent_id` | 同上 |
| `eip_sweep_handover` 3 天逾期升級 | `select manager_id ...` —— **既不往上找、也不檢查在職** | 無主管部門通知到 **null**；電宰會計課通知到**已停用的孫倩筠** |

### 修法
新增 `eip_dept_effective_manager(p_dept, p_exclude)`：從自己開始往上找第一個有
**在職** `manager_id` 或**明確登記督導**（0158 那張表）的部門。深度上限 20 防環狀 `parent_id`。
`p_exclude` 用來排除離職者本人（不能接自己的交接）。三處全部改用它。

### 驗證
