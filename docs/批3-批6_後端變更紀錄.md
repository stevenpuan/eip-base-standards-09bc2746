## 批3｜任務子項清單 — `0112` `0113`

### 新表 `task_checklist`

| 欄位 | 說明 |
|---|---|
| `task_id` | → `task(id)` **ON DELETE CASCADE** |
| `title` / `is_done` / `sort_order` | 子項內容、勾選狀態、排序 |
| `done_at` / `done_by` | 勾選時由 trigger 自動蓋、取消勾選自動清空 |
| `created_by` / `tenant_id` | 由 trigger 補，前端不用塞 |

**設計決策（避免反覆）**

- 用新表，**不沿用 `task.parent_task_id`** —— 子任務當成 task 會污染看板，現況已被迫 filter 掉
- 勾選語意＝「今天有做、納入回報」，**不是百分比**，所以**不自動改 `task.progress`**
- 不做「任務範本自動展開子項」（`task_type.default_steps` 維持現況，屬確定不做的項目）
- `task_id` 用 CASCADE：任務軟刪除時子項保留（還原後跟著回來）；建立者按「永久刪除」走
  `eip_purge_deleted` 時 guard 放行真 DELETE，子項一併清除
- `done_by` / `created_by` 一律 **SET NULL**，不重蹈 H6（CASCADE 被軟刪除 guard 靜默取消）的錯

### 配套

- `eip_can_edit_task_checklist(task_id)` — 與 `task_update_policy` 同一組人
  （owner / 建立者 / 協作者 / admin / 部門主管），並排除已軟刪除的任務。
  **沒有共用 `eip_can_manage_task`**，因為那支少了「建立者」與「協作者」且不看 `deleted_at`
- `eip_reorder_task_checklist(task_id, ids[])` — 拖曳排序一次寫回，不用 N 次 PATCH
- `task_checklist_summary` view — 看板卡片顯示「3/5」用，避免每張卡各發一次查詢
- RLS：可見範圍**完全跟隨母任務**。政策內的 `task` 子查詢會套用 task 自己的 RLS
  （含 `deleted_at is null`），所以「看得到任務就看得到子項」自動成立，不需複製一份 `task_read` 邏輯

> **0113 是修 0112 的漏洞**：view 預設以「建立者權限」執行會整段繞過 RLS，
> 讓任何登入者讀到全公司所有任務的子項統計。改 `security_invoker = true`。
> 之後所有新 view 一律加這個。

## 批4｜通用連結、行事曆休假、執行歷程、部門例行彙總 — `0114`

### `eip_link` 通用連結表

任務↔文件、會議決議↔任務、缺失↔任務… 用一張表表達，不再為每種組合開欄位。
`(from_type, from_id, to_type, to_id, relation)` 唯一，`relation` 限
`related / blocks / duplicates / source_of / follow_up`，並禁止自我連結。

**已知限制（寫在 table comment 裡）**：RLS 只能做到 tenant 層級 —— 無法在政策內動態檢查
兩端實體的可見性。前端解析兩端標題時仍要各自查原表（RLS 會擋），連結本身只是 id 對照。

### `eip_calendar_events` view — 行事曆終於看得到請假

把個人行程與請假（`eip_quick_report` where `type='leave'`）併成一個來源。
`leave_from` / `leave_to` 是 timestamptz，一律換算 **Asia/Taipei** 再取日期。
代辦未完成的假會在標題後標「（代辦未完成）」。

`security_invoker=true` 讓兩邊各自的 RLS 生效：本人看自己的、主管看管轄範圍的，
**不會因為併成 view 就讓全公司看到彼此的假**。

實測正式資料：**58 筆（個人行程 45 + 請假 13）**。那 13 筆請假就是原本上不了行事曆的資料。

### `eip_task_timeline` view — 執行歷程時間軸

合併三個來源，**不新增表**：

| kind | 來源 |
|---|---|
| `field_change` | `task_change_log`（標題/狀態/負責人/優先級/期限…逐欄變更） |
| `progress` | `task_update`（進度回報 + 留言 + 狀態切換） |
| `checklist_done` | `task_checklist`（子項完成） |

三個來源都已有 RLS SELECT 政策，`security_invoker` 直接沿用。
實測正式資料：**285 筆（欄位變更 163 + 進度回報 122）**。

### `eip_dept_routine_summary(from, to, dept)` 部門例行彙總

- **應做**＝當日到期的個人例行範本（複用既有 `eip_personal_routine_due_on`）
- **已做**＝工作日誌上午/下午區裡 `source='personal_routine'` 且 `done=true` 的項數
- **分母口徑**：只算「當日有到期範本」或「當日日誌有勾到例行項」的人日，
  沒有任何例行範本的人不會被算進來（避免分母灌水）
- 一次最多查 92 天

> **目前回傳 0 列是正常的** —— `personal_routine` 現在有 0 筆啟用資料，
> P0-3 的範本頁今天才上線，還沒有人建立自己的例行範本。

## 批5｜異常缺失 / CAPA 模組 — `0115` `0116`

### 狀態機（雙軌）

```
主管開立  pending_fill 待填報 ─┐
                              ├→ filled 已填報 → improving 追蹤改善中 → closed 已結案
員工自主填報 ────────────────┘
                                    void 作廢（只有主管／管理者）
```

`source='self'` 直接從 `filled` 起算，由 CHECK constraint 保證不會出現
「自主填報卻是待填報」的狀態。

### 追加需求全部落實

| 需求 | 實作 |
|---|---|
| 主管開立缺失，記錄開立日期時間 | `raised_by` / `raised_at`，單號 `AN-YYYYMM-序號` 由 trigger 產生 |
| 格式簡易可貼截圖 | `attachment_entity` enum 加 `anomaly`，沿用既有 attachment 表 |
| 通知員工 → 員工點通知進填報 | `anomaly_opened` **urgent → 立即推播**，訊息含填報期限 |
| 狀態機加起始狀態「待填報」 | `pending_fill` |
| 週彙整 KPI 加「未填寫」 | `eip_anomaly_weekly_kpi` 的 `unfilled` 欄（另有 `overdue_unfilled`） |
| 唯一保留的主管簽核＝確認並追蹤改善 | `status → improving`，蓋 `confirmed_by` / `confirmed_at` / `confirm_note` |

### 8 題待確認採用的建議預設值

| 題目 | 採用值 |
|---|---|
| 主管開立是否設限期填報 | **是，開立日 + 3 天**（`fill_due_date`） |
| 員工能否退回缺失 | **否** —— 沒有 reject 動作，只能填報或請主管作廢 |
| 異常金額是否必填 | **非必填**（`amount` nullable，只約束 >= 0） |
| 遲到回報是否保留 | **保留在 `eip_quick_report`**，不併進本模組 |

### 通知（4 個事件 + 1 個排程）

| 事件 | 收件範圍 | 優先級 | LINE |
|---|---|---|---|
| `anomaly_opened` 主管開立 | owner（責任員工）+ deputy | **urgent → 立即推播** | 開 |
| `anomaly_filled` 填報完成 | dept_manager + 開立者 | normal → 彙整 | 開 |
| `anomaly_confirmed` 確認追蹤 | owner | normal | 開 |
| `anomaly_closed` 結案 | owner | normal | 關 |
| `anomaly_overdue` 逾期未填報 | owner + dept_manager | high | 開 |

**全部走 `eip_emit_notification` 統一入口，沒有任何一支直接呼叫 `net.http_post`。**

`eip_notification_recipients` 查不到啟用的 `notification_setting` 就**完全不發**，
所以 5 筆設定列一併建好 —— 少了這步整個模組的通知會靜默失效。

逾期掃描 `eip_sweep_anomaly_overdue()` 排程在**台北 00:30（UTC 16:30）**，
靠 `eip_emit_notification` 的 20 小時去重節流，不會天天重打同一則。

### RLS（5 條政策）

- 讀：本人（責任員工）／開立者／部門主管（含子部門）／管理者
- 開立：部門主管、管理者，或員工替自己開自主填報
- 填報（`anomaly_fill`）：只有責任員工本人，且 **WITH CHECK 也綁 `subject_id`**，避免把單子改到別人頭上
- 管理（`anomaly_manage`）：主管確認/結案/作廢，**WITH CHECK 也要求改完之後仍在自己管轄範圍內**
  —— M8 的教訓：PERMISSIVE 政策之間是 OR，WITH CHECK 太寬會放寬其他政策的限制
- `subject_id` 用 **ON DELETE RESTRICT**：有缺失紀錄的員工不允許硬刪

### 納入回收區

`eip_deletion_policy` 加一列，`purge_role = **admin**`（不是 `creator`）——
缺失紀錄涉及稽核，不讓開立者自己永久刪。

### 實測（正式庫，已清除）

開立 → 填報 → 確認追蹤 → 結案四段狀態全走一遍，四則通知都正確發出且優先級正確
（只有開立是 urgent 立即推播，其餘 normal 走彙整）；單號 `AN-202607-001`、
`fill_due_date` 自動 +3 天；軟刪除 guard 正確把 DELETE 轉成 `deleted_at`；
KPI 函式回傳正確。測試資料已用 `eip.allow_purge` 永久清除。

## `0118`｜修正我自己在 0110–0117 造成的授權缺口

**這是一個我造成的正式環境漏洞，advisor 抓到，同一天內修掉。**

Postgres 建立函式時預設把 `EXECUTE` 授給 **PUBLIC**。我在 0110–0117 寫的
`revoke execute ... from anon, authenticated` 是 **no-op** ——
權限來自 PUBLIC 這個偽角色，不是 anon/authenticated 的個別授權。

`has_function_privilege('anon', ...)` 實測：我當天新建的 14 支函式**全部是 true**。

### 實際影響

- `POST /rest/v1/rpc/eip_sweep_anomaly_overdue` **未登入即可呼叫** → 可觸發大量通知
- `eip_performance_summary` / `eip_dept_routine_summary` / `eip_anomaly_weekly_kpi`
  的守衛寫成 `if auth.uid() is not null and role not in (...)` ——
  anon 的 `auth.uid()` 是 null，**整條守衛被略過** → 未登入可讀全公司績效與部門例行資料

### 兩層都修

1. **收回 PUBLIC 的 EXECUTE**：內部／觸發／排程函式對 PUBLIC + anon + authenticated 全收，
   只留 postgres 與 service_role（cron 與 trigger 都以 owner 身分執行）；
   前端要用的 7 支 RPC 收回 PUBLIC + anon，明確只 grant 給 authenticated
2. **守衛改 fail-closed**：4 支報表函式改成 `if auth.uid() is null then raise` —— 
   這幾支都不由 cron 呼叫，不需要保留「無身分可執行」的後路。
   （`CREATE OR REPLACE` 會重設 ACL，所以重寫後要再收一次權限）

### 結果

anon 可呼叫的 public 函式從 **24 支降到 2 支**：`eip_has_perm`、`eip_worklog_file_access`。
兩支都是既有函式、都是 storage / RLS 政策的輔助函式，且對 anon 而言
`auth.uid()` 為 null 必然回 false / 無權限。**刻意不動** ——
它們被 storage 政策引用，上線前 3 天改授權的風險大於收益。

排程驗證：7 個 cron job 全部 active，`eip_sweep_anomaly_overdue` /
`eip_confirm_line_delivery` / `eip_sweep_handover` 在收權後仍正常執行。
