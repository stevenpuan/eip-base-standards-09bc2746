# 通知／LINE 第三輪稽核與修正紀錄（2026-07-28）

掃描範圍（含使用者指定的兩類盲點）：

- **盲點 A｜表上的 trigger** — public schema 全部 **59 個 trigger / 32 張表**逐一判讀
- **盲點 B｜外部服務的真實回應** — **7 個對外呼叫點 + 4 個 Edge Function**，比對 `net._http_response` 84 筆實際回應
- 另含 42 個 `SECURITY DEFINER` 函式、8 條 RLS 政策、0106–0108 逐項驗收

結果：新發現 **高 6、中 15、低 7**。0106–0108 共 20 項，成立 14、部分成立 4、不成立 2。

---

## 兩類盲點掃出什麼

### A. 表上的 trigger

`notification` 表 **0 個 trigger** — `trg_notify_line` 確認已清除，全庫沒有任何 trigger 在吞例外（`exception when others then return new/null` 命中 0 筆）。統一入口沒有旁路。

新發現兩處：

1. **`user_roles` 上兩支 trigger 都在改 `app_user.role`**（M6）
   同表同事件按 **trigger 名稱字母序**執行：
   `trg_audit_user_roles` → `trg_sync_app_role`（現行）→ `trg_sync_app_user_role`（**legacy，最後跑、覆蓋現行結果**）。
   兩者映射不一致：`member + viewer` 併存時新版判 `viewer`、舊版判 `member`。
   舊版勝出 → `current_role_name()` 走 member 分支 → `task_insert` / `document_insert` 白名單通過
   → **本該唯讀的帳號可以建立任務與文件**。舊版還缺 `is distinct from` 守衛，每次角色調整寫 2 筆 audit_logs。

2. **軟刪除 guard 的 `return null` 靜默取消 `ON DELETE CASCADE`**（H6）
   `personal_event` / `personal_routine` / `work_log` → `app_user` 這三條 FK 是 CASCADE。
   刪除員工時 cascade 的子表 DELETE 被 guard 取消 → 留下違反外鍵的孤兒列，**不報錯**。

另外逐張驗證了 guard 的 UPDATE 會不會誤觸同表其他 trigger — **8 張表全部安全**
（`trg_qr_handover_done` 靠兩道提早返回擋住、`trg_task_change_log` 逐欄比對後不寫 log、
`trg_announcement_notify_upd` 是 `OF published_at` 不在 SET 清單內故不觸發）。

### B. 外部服務的真實回應

`net._http_response` 84 筆實際分佈：

| line_status | 筆數 | 判讀 |
|---|---|---|
| 429 額度用盡 | **69** | H4 永久卡死 |
| 500 | 4 | 重試 |
| **200 真的送達** | **11** | 送達率 13% |
| DNS 逾時 5000ms | 1 | M5 |

**「DB 認為成功但外部其實失敗」的案例：0 筆。** 0106 的雙層驗證（HTTP 2xx **且** `line_status` 2xx）
確實把假訊號消除了。

但殘留三處「HTTP 200 就當成功」：

- `line-webhook` 的 `reply()` / `replyWithConfirm()` — **連 status code 都沒讀**，回傳值直接丟棄，DB 無紀錄
- `line-push` 兩個 skip 分支（缺 token、未綁 LINE）回 200 但 body 沒帶 `line_status`
  → DB 判為失敗、重試 3 次後寫「HTTP 200（已重試 3 次）」，訊息完全誤導
- `line-webhook` 對 Anthropic 的呼叫有 fallback 但只寫 console，DB 無紀錄

## 已修正（0109 / 0110 / 0111 + line-webhook v16）

### 0109 上線前必修

| 項目 | 內容 |
|---|---|
| **M6** | `drop trigger trg_sync_app_user_role` + `drop function sync_app_user_role()`。角色映射收攏成單一來源：`current_role_name()` 改委派 `eip_derive_app_role()`。**套用前比對 26 位員工，推導結果 0 筆差異** |
| **H1** | `revoke execute on eip_build_handover(uuid) from anon, authenticated`。這支只該由 `trg_user_status_handover` 觸發；它尾端兩個 UPDATE（停用常態工作、清除代理人）不受 RLS 約束也無範圍限制 |
| **H5** | `eip_pending_reassign` 的 task / task_collaborator 分支補 `t.deleted_at is null`；`eip_sweep_handover` 的完成判定也把軟刪除視為已結案。<br>這批表中**只有 `task` 有軟刪除**，project / recurring_rule / meeting_action_item / app_user 仍是硬刪 |

> **關於 H1 的實際嚴重度**：`eip_build_handover` 內部呼叫的 `eip_pending_reassign` 本來就有
> 「僅 company_admin / dept_manager」的守衛，而那個 loop 在函式尾端兩個 UPDATE 之前，
> 所以一般 `member` 呼叫會直接拋例外、整個交易回滾 —— **稽核報告說「任何員工」是高估了**。
> 實際可利用者是 **dept_manager**：他可以拿任一員工的 uuid 停用對方全部常態工作、
> 清掉全公司指向對方的代理人設定。仍屬必修，但範圍比報告小。

### 0110 LINE／通知可靠性

新增兩個欄位取代「靠 `line_error` 字串比對」的做法：

- `notification.line_queued_at` — 真正排入 pg_net 佇列的時間
- `notification.line_blocked_until` — 額度用盡等暫時性阻擋的解除時間

| 項目 | 修法 |
|---|---|
| **H3** | 「回應遺失 15 分鐘」原本用 `created_at`（通知建立時間），對彙整推播等於**零寬限期** → 回應還在路上就被判遺失 → 重複推播。改用 `coalesce(line_queued_at, created_at)` |
| **H4** | 429 原本寫進 `line_error` 再被兩支排程用 `not like '%額度已用盡%'` 排除，而沒有任何機制清掉 → **永久卡死**，與訊息文字「額度重置後會自動重送」矛盾。改成寫 `line_blocked_until = 下個月 1 號`，到期自動放行；另加 **30 天絕對上限**避免佇列無限累積 |
| **M1** | 立即推播分支沒檢查 `rec.line_enabled`；exception handler **無條件**把 `line_pending` 設 true，等於繞過「該事件已關閉 LINE」的設定。改為 `if v_urgent and rec.line_enabled`，handler 改 `line_pending = rec.line_enabled` |
| **M2** | 去重鍵含【緊急】/【重要】前綴 → 同事件升級優先級會發兩次。改成比對「去掉前綴後的訊息」，並在真的升級時**改寫既有那一列**（提升 priority、加前綴、重開 LINE、標回未讀），既不重複也不靜默吞掉 |
| **M3** | digest 的 WHERE 原本是 retry 的**超集**，兩支都沒有行鎖，digest 單輪最壞約 6 分鐘會跨進 retry 的分鐘 → 同一批推兩次。改用**優先級分工**讓兩者集合互斥（high/urgent → retry，其餘 → digest），比加行鎖乾淨 |
| **M4** | `r.content::jsonb` 無 JSON 驗證，平台層回 HTML/純文字會讓整支確認排程拋錯 → **送達確認全面停擺 6 小時**（pg_net 回應保留 6h，每 5 分鐘重試都撞同一列）。新增 `eip_try_jsonb()` / `eip_line_status()` 安全轉換，外層再包 exception 並寫入 `eip_notification_miss` |
| **M5** | `eip_line_push_now`（**最重要的立即推播路徑**）仍是預設 5000ms，而實測已有「光 DNS 就吃掉 5000.79ms」的逾時案例。補 `timeout_milliseconds := 15000` |
| **M10** | 「recipients 非空但 `in_app` 全 false」原本靜默丟棄且不留紀錄（設定畫面上「只發 LINE 不發站內」看起來合法，實際什麼都不發）。改為分開記錄兩種漏發原因；miss 寫入失敗改 `raise warning` 而非完全靜默 |
| **M12** | `revoke all on notification from anon`、`revoke insert from authenticated`。原本是「靠 RLS 剛好擋住」而非授權面乾淨 |
| **M14** | `create unique index uq_app_user_line_user_id`。一個 `line_user_id` 綁到兩人時 `maybeSingle()` 會報錯讓助理整體癱瘓，且推播會送錯人。套用前確認 0 筆重複 |

### 0111 軟刪除範圍、交接節流、權限收斂

| 項目 | 修法 |
|---|---|
| **H6** | 三條 FK（`personal_event` / `personal_routine` / `work_log` → `app_user`）CASCADE 改 **RESTRICT**。員工有這些資料時不允許硬刪，必須明確處理 |
| **M7b** | 0095 只改了 8 條 SELECT 政策。這次把 **19 條 UPDATE / DELETE / ALL 政策**的 USING 補上 `deleted_at is null`。<br>**只加在 USING，不能加在 WITH CHECK** —— 否則軟刪除自己那筆 UPDATE 會被擋掉 |
| **M8** | `qr_update_done` 缺 tenant_id、缺 deleted_at、缺 WITH CHECK，PERMISSIVE 之間是 OR，把 `qr_update_own` 的「只有 open 才能改自己的」整條放寬。重建為只允許 `type = 'leave' and status <> 'done'`，並補上 tenant + WITH CHECK |
| **M9** | 新增 `eip_soft_delete(p_module, p_id)` RPC（SECURITY INVOKER，RLS 照常生效），回傳明確的 `{ok, deleted_at}`。guard 的 `return null` 會讓 PostgREST 回「0 列受影響」，前端若寫 `.delete().select()` 或檢查筆數會誤判成「刪除失敗」 |
| **M11** | `eip_sweep_handover` 在通知失敗（部門沒設主管）時不推進層級 → 每天重試、每天寫一筆 miss、永久累積且沒人被通知。新增 `last_notify_at` / `notify_attempts`：同層級每 20 小時最多試一次，連 3 次失敗就強制推進並只留一筆紀錄 |
| **L2** | `eip_restore_deleted` 補 `deleted_at is not null` 檢查 |
| **L4** | 8 支觸發函式收回 anon / authenticated 的 execute |
| **L6** | `eip_priority_label` / `eip_handover_touch` 補 `search_path` |

### line-webhook v16（Edge Function）

| 項目 | 修法 |
|---|---|
| **H2** | 簽章驗證改 **fail-closed**。原本 `if (secret) { ...verify... }` 沒有 else，一旦 `LINE_CHANNEL_SECRET` 缺失就變成公開的 service_role 後門（此函式 `verify_jwt=false`）。改為缺 secret 直接回 500。<br>**部署前已用壞簽章實測確認 secret 存在**（回 401 bad signature），才敢改 fail-closed |
| **M7a** | 這支用 service_role **完全不受 RLS 約束**，所有工具查詢補 `.is("deleted_at", null)`（task ×4、personal_event、announcement、eip_document）。原本員工把文件丟進回收區後，在 LINE 問「幫我找 XXX」照樣讀得出來，已刪任務也會被算進逾期統計 |
| **M13** | `reply()` / `replyWithConfirm()` 改回傳 boolean 並檢查 LINE 回應，失敗寫入 `eip_notification_miss`；`eip_assistant_message` 的對話紀錄會標「（LINE 回覆未送達）」。原本額度用盡期間員工在 LINE 問問題 → Anthropic 被呼叫產生費用、對話紀錄寫入、**LINE 那頭什麼都沒收到**，管理者查紀錄卻看到「有正常回覆」 |
| **M14** | 綁定前先 `update app_user set line_user_id = null where line_user_id = <this> and id <> <target>`；`maybeSingle()` 報錯時不再退回「當綁定碼處理」分支 |
| **M15** | `search_documents` 的 `.or()` 過濾掉 PostgREST 語法字元（逗號分隔條件、括號分組），避免改寫過濾樹 |
